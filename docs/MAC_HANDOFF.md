# HealthMi 1.2.0 签名覆盖安装交接

以 GitHub Actions 产物中的 `source-commit.txt` 为准。此 IPA 没有 Apple 签名；附带的 `HealthMi.entitlements` 是签名输入，不能代替有效描述文件。应用版本 1.2.0（2），iOS 17.0+，源工程 Bundle ID 仍为 `com.healthmi.HealthMi`。

## Mac 上的 Codex

1. 下载同一成功 Actions 运行的 `HealthMi-unsigned-<提交号>` 和构建结果，核对 IPA 的 SHA-256、提交号和测试结果。
2. 先检查 Mac、iPhone 系统版本和当前安装版本的签名标识。用户是普通免费 Apple 账号；不要假定任意侧载工具都能授予 HealthKit。签名和描述文件都必须允许 `com.apple.developer.healthkit`。
3. **使用与手机现有版本相同的 Apple 账号/团队和最终 Bundle ID 覆盖安装；不先卸载，不随意改 Bundle ID 或 Keychain 访问组。** 某些签名工具会改 Bundle ID，需以现有安装为准。否则不能保证保留 App 容器和凭据，也可能改变 HealthKit 来源身份。
4. 本次未修改 SwiftData schema、存储路径或 Keychain service；无需清库或迁移个人数据。签名证书、私钥、密码与个人数据只在用户设备处理，不传入 GitHub 或聊天。
5. 不需要重新修改同步逻辑来签名，不通过删除 HealthKit 权限让 IPA 勉强装上。安装成功后先验证版本及健康授权，再由用户决定真实同步。

## 已有自动验证及仍需真机验证

- 原有 XCTest 与新增日期边界、分页保护、后台完成回调、SwiftData 重复回填等测试由 CI 执行；具体数量和状态见 `test-results.json`。
- `virtual-app.log`、`virtual-engine.log`、`virtual-stress.log` 是虚构数据的离线场景，覆盖游标不变、取消、互斥、其他来源和范围外数据保护等；不使用真实小米凭据或健康数据。
- 模拟器/替身测试不能验证实际小米响应、HealthKit 真机锁屏行为、系统后台调度频率或耗电。

## 安装后使用

- 「重新回填历史」可选 7/30/90/全部（最近 3650 天）或自选日期，按区域时区包含起止两天，确认框显示实际范围。
- 单次查询保持最多 200 页和游标循环保护，不承诺统一可回填天数。超限按月、周或天缩短范围；已完成类型可以重复回填。
- 历史回填不建立或更改日常增量游标。首次增量仍须前台完成（默认最近 30 天）；后台仅处理已有游标的类型。
- 自动同步开关默认关闭，开启后以一小时为最早目标间隔。实际由 iOS 调度；不是每小时定时器。历史游标落后时，后台每轮最多向前追赶一个日历日，同时保留一天回看。
- 历史页面保留最近 50 轮的起始时间、耗时、前后台模式、结果、请求数/重试数/页数。计数包含应用主动发起的登录和数据请求，不单独统计 URLSession 内部重定向。不记录账号、Token、URL、请求体或健康数值，也不会上传指标。
- 健康数据保存和删除不能组成跨 API 原子事务。保存后取消或清理失败可能暂留本应用的重复样本；重跑同一历史范围以清理。不会因此推进该失败类型的游标。

建议真机观察一两天的实际调度间隔和上述指标，再结合 iOS 电池页面评估耗电；不能用 CI 耗时推算手机耗电。
